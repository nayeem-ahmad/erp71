# External-sync match review — design

**Date:** 2026-09-21
**Status:** Approved for planning
**Context:** Towfiq Traders migration — ExpressRetail (Mitford branch) + Dizi Cashier (Press Club branch)

---

## Problem

The external-sync importer matches records from a legacy ERP to existing
ERP71 records by exact string equality and nothing else:

| Entity | Current match | File |
|---|---|---|
| Product | `{ tenant_id, sku }` | `external-sync.service.ts:619` |
| Customer | `{ tenant_id, OR: [phone, customer_code] }` | `external-sync.service.ts:713` |
| Supplier | `{ tenant_id, name }` | `external-sync.service.ts:824` |

Three consequences:

1. **Near-misses create duplicates.** "Beximco Pharma Ltd" and "Beximco
   Pharmaceuticals Limited" become two suppliers.
2. **Matching is invisible until after it has happened.** A match writes an
   `ExternalSyncMapping` row and posts documents against the adopted record;
   the `ADOPTED_EXISTING` warning is emitted *after* the write. Nobody
   approves a match before it becomes permanent.
3. **Products carry no reliable identity.** `Product` has no barcode column
   and `sku` is nullable, so cross-source product identity is free-text name
   only.

Towfiq Traders imports two sources into one tenant, so the second import
meets parties the first one created. Getting this wrong means documents
billed to the wrong supplier, with no undo — `isImmutablyPosted` refuses to
rewrite a posted document.

## Approach

Matching runs during a **dry run** and produces a **spreadsheet of proposed
matches**. A human decides in Excel. The completed sheet is uploaded, the
decisions become `ExternalSyncMapping` rows, and the **live run consumes
those mappings** and writes nothing ambiguous.

No staging table, no review UI, no `pg_trgm`. The workbook *is* the review
queue, and it doubles as the migration's audit record.

```
dry run ─→ normalize ─→ block ─→ score ─→ XLSX download
                                              │
                                    human fills `decision`
                                              │
              ExternalSyncMapping ←─ upload ←─┘
                                              │
                                        live run
```

### Why a spreadsheet rather than a review screen

This is a one-time migration for one tenant. A review screen costs a
migration, endpoints and a page, and is dead code the day after the import.
A spreadsheet is reviewable offline, by someone who knows the shop's
suppliers and is not an app user, and it leaves a file that records what the
migration decided.

## Matching

### Normalization (shared)

Applied before any comparison:

- Unicode NFC (so composed/decomposed Bengali compare equal)
- Bengali digits ০-৯ → 0-9
- case-fold, collapse internal whitespace, trim
- strip punctuation

### Per-entity strategy

Matching is **tiered per entity**, not one generic similarity score.

**Customers — phone is identity.** Normalize to `+8801XXXXXXXXX` (strip
leading `0`, `88`, `+88`). Exact match on normalized phone auto-links. No
fuzzy matching.

> **Fix:** `customer_code` is removed from the match `OR`. Codes are
> provider-generated by `dedupeCode` (`external-sync.mapper.ts:112`), so an
> Express `C-101` can collide with an unrelated Dizi or pre-existing
> customer. A code is not identity. Customers with no phone fall through to
> review rather than matching on code.

**Suppliers — normalized name.** Additionally strip corporate suffixes
(Ltd, Limited, Co, Company, Enterprise, Traders, & Sons). Exact after
normalization auto-links; near-miss goes to review. Volume is low (~36 on
the probed Dizi account), so review is cheap.

**Products — blocking key, then similarity within the block.**

The two expected name variations pull in opposite directions:

- brand prefix inconsistency ("Napa" vs "Square Napa") wants *loose* matching
- pack/strength suffixes ("Napa 500mg" vs "Napa 665mg") demand *strict*
  matching — these are different products and must never merge

Resolved by **blocking on the invariant part**: extract strength and pack
tokens (`500mg`, `10s`, `100ml`) and require them to match **exactly** for
two products to be considered candidates at all. Brand-prefix tolerance
applies only *within* a block.

`Napa 500mg` and `Napa 665mg` land in different blocks and can never pair,
whatever their string similarity. `Napa 500mg` and `Square Napa 500 mg`
share a block and match on the remaining tokens.

Similarity within a block is token-set based (Jaccard over normalized
tokens), which handles a missing brand prefix as a subset rather than a
string-distance penalty.

### Confidence tiers

| Tier | Meaning | Pre-filled decision |
|---|---|---|
| `high` | exact after normalization, or single in-block candidate above the upper threshold | `accept` |
| `medium` | in-block candidate in the middle band, or several plausible ones | *blank — needs a human* |
| `low` | weak candidate | `new` |
| `none` | no candidate | `new` |

Only `medium` rows require attention. `high` and `low`/`none` arrive
pre-filled and can be scanned or overridden.

Thresholds are constants, tuned against the first real dry run, not guessed
in advance.

## The workbook

One sheet per entity plus a manifest. Every source row appears, including
auto-matched ones — the workbook is the complete record of what the import
decided, not just the hard cases.

**Sheets:** `Manifest`, `Products`, `Customers`, `Suppliers`

`Manifest` is read-only metadata: tenant, connection ids, provider, dry-run
id, window, generation timestamp, row counts. It is what the upload
validates against.

**Columns** (per entity sheet):

| Column | Editable | Purpose |
|---|---|---|
| `external_id` | no | round-trip key |
| `source` | no | `ExpressRetail` / `Dizi` |
| `source_name` | no | name in the legacy ERP |
| `source_extra` | no | strength/pack, phone, or code |
| `suggested_match` | no | best ERP71 candidate (blank if none) |
| `match_id` | no | candidate's ERP71 id |
| `confidence` | no | high / medium / low / none |
| `alt_candidates` | no | next 2–3 options |
| `alt_ids` | no | their ids |
| **`decision`** | **yes** | `accept` / `new` / `alt1` / `alt2` / `alt3` / `skip` |
| `notes` | yes | free text, round-trips for the audit trail |

`decision` gets an Excel data-validation dropdown.

Sorting puts `medium` rows first, so the work that needs a human is at the
top of each sheet.

### Round-trip safety

The upload is the dangerous half — a mangled or stale file could mislink
records permanently. Validation rejects the whole file (never partially
applies) when:

- the manifest's connection ids or dry-run id do not match the target
- any `external_id` is unknown, duplicated, or missing
- a `decision` is not one of the allowed values
- `alt1`/`alt2`/`alt3` is chosen where no such alternative was offered
- a referenced `match_id` no longer exists, or is soft-deleted
- the file's row count disagrees with the manifest

A stale file — generated before another import changed the tenant — is
caught by the `match_id` existence check and the dry-run id.

Decisions are persisted as `ExternalSyncMapping` rows, which already carry
`@@unique([connection_id, entity_type, external_id])`. Re-uploading a
corrected file updates in place. **No new table.**

## Implementation

Reuses the codebase's established spreadsheet pattern (browser-side
parse/write, JSON over the wire). No backend XLSX library.

### Backend — `apps/backend/src/external-sync/`

| File | Change |
|---|---|
| `match/normalize.ts` | **new** — NFC, digits, case, suffixes, phone |
| `match/blocking.ts` | **new** — strength/pack token extraction, block key |
| `match/score.ts` | **new** — token-set similarity, confidence tiers |
| `match/candidates.ts` | **new** — build candidate rows for a dry run |
| `external-sync.service.ts` | adoption paths consult mappings first; the three fixes below |
| `external-sync.controller.ts` | `GET …/match-candidates`, `POST …/match-decisions` |
| `tenant-external-sync.controller.ts` | same two routes, owner-gated |

The new `match/` directory keeps this out of `external-sync.service.ts`,
already ~2000 lines.

`GET match-candidates` returns JSON rows; the browser writes the XLSX.
`POST match-decisions` accepts `{ manifest, rows }` as JSON.

### Frontend

| File | Change |
|---|---|
| `lib/spreadsheet.ts` | **extend** `parseSpreadsheetFile(file, sheetName?)` |
| `settings/data/external-import/page.tsx` | download / upload controls |
| `lib/api.ts` | two calls following the existing import-fn shape |

> **`parseSpreadsheetFile` currently reads only the first sheet**
> (`wb.SheetNames[0]`, `spreadsheet.ts:31`). A multi-sheet workbook would
> silently lose three tabs. An optional `sheetName` parameter is
> backward-compatible with all 15 existing `ImportDialog` callers.

Export uses the existing `exportToExcel` approach (`export-utils.ts:115`,
dynamic `import('xlsx')`), extended to write multiple sheets and a
validation dropdown.

`ImportDialog` is **not** reused — it is built for map→preview→upsert against
arbitrary headers. This is a fixed-schema decisions round-trip keyed on
`external_id`.

> **Row cap:** `ImportRowsDto` caps at 5000 (`common/import.dto.ts`). Two
> sources × (~500 products + ~250 customers + ~36 suppliers) fits, but the
> decisions endpoint takes its own DTO with a cap sized to the manifest
> rather than borrowing the 5000 constant.

### Three fixes folded in

These are in the code being changed and affect the same correctness:

1. **Supplier tombstone adoption** (TODO.md:357) —
   `external-sync.service.ts:826` has no `deleted_at: null`, so a supplier
   can be adopted into a soft-deleted tombstone and mapped to it
   permanently. The workbook makes the balance question tractable: a
   reviewer sees "matches a deleted supplier" and chooses, rather than the
   importer silently deciding. A revived supplier keeps its prior
   `due_balance`, so `applyOpeningBalance` must not also run — the existing
   `!adopted` guard already handles this once the match is explicit.
2. **Customer `OR` on `customer_code`** — removed, per above.
3. **`deleted_at: null` on all three adoption queries** — products and
   customers have the same latent issue as suppliers.

## Testing

Unit tests, no live ERP needed:

- `normalize.spec.ts` — Bengali digits and script, suffix stripping, phone
  forms (`01712…`, `8801712…`, `+8801712…`)
- `blocking.spec.ts` — **`Napa 500mg` and `Napa 665mg` never share a
  block**; `Napa 500mg` / `Square Napa 500 mg` do; `10s` vs `(10 pcs)`
- `score.spec.ts` — brand-prefix subset scores high; unrelated names low;
  tier boundaries
- `candidates.spec.ts` — every source row produces exactly one output row;
  pre-filled decisions per tier
- `decisions.spec.ts` — **rejection cases**: unknown/duplicate
  `external_id`, bad `decision`, `alt2` with no alt2, deleted `match_id`,
  manifest mismatch, count mismatch. All-or-nothing.
- `spreadsheet.test.ts` — extend for `sheetName`; existing callers unaffected

Note `external-sync.service.spec.ts` does not exist (TODO.md:140) — the
write path has no coverage. Not fixed here, but the new `match/` modules are
pure functions and fully testable.

## Out of scope

- **Warehouse attribution.** External-sync writes no `warehouse_id`
  (TODO.md:638), so "main warehouse" cannot be honored. Separate work;
  affects where imported stock lands.
- **Dizi `post_impacts`.** Off by default. Dizi exposes a *current* balance,
  not an opening one, so enabling posting double-counts (TODO.md:180).
  Decide before the live run.
- **First live Dizi write.** No non-dry Dizi run has ever executed
  (TODO.md:176). Walk it one step at a time via `steps`.

## Open question

Whether Mitford and Press Club share parties is unknown. The first dry run
answers it: a high count of `medium` supplier rows in the second source means
heavy overlap. **Import order matters** — run one source fully, review, apply,
*then* the second against the now-populated tenant, so the second source's
candidates include what the first created.
